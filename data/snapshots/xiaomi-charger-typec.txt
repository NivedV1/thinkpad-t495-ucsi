port0 never received a partner during the capture, so both attaches landed on
the same UCSI connector, port1 / _SB.UBTC.CR02.

Same port, same charger, same cable. The only value that changed at the partner
level was supports_usb_power_delivery: no -> yes. The live port state
(power_operation_mode) was usb_power_delivery on both sides of the replug.

Kernel-side reason: supports_usb_power_delivery is desc.usb_pd, captured once in
ucsi_register_partner() from UCSI_CONSTAT(PWR_OPMODE). power_operation_mode is
set later by ucsi_pwr_opmode_change(). If the EC answers "default" at partner
registration and "PD" a few seconds later, the partner keeps "no" for the whole
attach while the port reports PD and a PD object exists. See docs/pd-verdict.md.

RDO-derived PSY values on this attach:
  current_now = rdo_op_current(rdo) = 3250 mA
  voltage_now = 0 mV, although the RDO selects position 4

Both are truncation artefacts, not a bad RDO. This firmware returns one PDO per
GET_PDOS request, so Linux records a one-entry capability list:
src_pdos[3] is zero (hence voltage_now = 0) and the last available entry is
src_pdos[0] = 5 V / 3 A. The RDO itself selects position 4 at 3.25 A, which is
the 20 V profile. See the top-level README §2-§3.
