WHAT THE TWO ATTACHES AGREE ON

1. The adapter is a 65 W part rated 20 V / 3.25 A. The only source capability
   the Linux driver ever shows for it is a single 5 V / 3 A fixed supply,
   because this firmware returns one PDO per GET_PDOS request and Linux asks
   only once. Windows walks offsets 0-3 on the same machine and gets
   5 V / 3 A, 9 V / 3 A, 15 V / 3 A and 20 V / 3.25 A.

2. The Request Data Object 0x43051545 selects object position 4, which is the
   20 V profile, at 3.25 A -> 65 W. The battery taking 17.37 W at 11.63 V is
   well inside that contract. There is no power-conservation paradox.

3. The PSY values are computed from that truncated list: voltage_now indexes
   src_pdos[rdo_index - 1] = src_pdos[3] and reads 0 V; voltage_max and
   current_max come from src_pdos[0] and read 5 V / 3 A; current_now comes
   from the RDO and reads 3.25 A. They are one short read, not a fabricated
   negotiation.

4. supports_usb_power_delivery is not a property of the adapter. It read "no"
   for eight minutes on attach A and "yes" for the whole of attach B, with the
   same adapter, port and cable state. Only the connector's orientation changed,
   which forces a fresh attach - and a fresh attach takes a new snapshot of the
   EC's PWR_OPMODE at partner-registration time (ucsi_register_partner()).

5. On attach B the partner PD object existed at 23:28:25 but was still unlinked
   one second later, then linked at 23:28:26. ucsi_register_partner_pdos()
   creates con->partner_pd first and only calls
   typec_partner_set_usb_power_delivery() after both GET_PDOS calls succeed, so
   a failed capability read leaves an orphan PD object and an unlinked partner.

Raw 1 Hz lines for both attaches were captured outside the repo; the transitions
above are the complete set of state changes in the 4-minute window covering the
flip. See docs/pd-verdict.md for the kernel-side explanation.
